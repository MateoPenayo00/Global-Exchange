Referencia — realm exchange‑learning

Guía de acceso de Exchange Pro

Cómo funcionan de punta a punta el inicio de sesión y el registro, dónde vive la consola de administración de Keycloak, y el error de "issuer" (emisor) que estuvo bloqueando cada login hasta hoy.

Stack Django 5.1 + mozilla‑django‑oidc + Keycloak 25.0.6 Realm exchange-learning Actualizado 4 sep 2026

Dos puertas hacia el mismo realm

Toda petición llega o bien desde un navegador a través de nginx, o bien desde el contenedor de Django hablando directamente con Keycloak. Las dos puertas deben declarar el mismo nombre de host, o Keycloak rechaza el token.

La regla: cualquiera sea el nombre de host que el navegador usó para llegar a nginx — localhost, 127.0.0.1 o una IP de LAN — cada llamada posterior de servidor a servidor de esa misma sesión debe presentar exactamente esa cadena como su cabecera Host, aunque físicamente se conecte a keycloak:8080 en la red de Docker.

Flujo de inicio de sesión y registro

Tanto /login/ como /register/ terminan en el mismo intercambio de OpenID Connect; el registro solo añade kc_action=register para que Keycloak abra su pestaña de alta en lugar de la de inicio de sesión.

1

Django redirige a Keycloak navegador

views.login_view / register_view envían al navegador a oidc_authentication_init, que construye la URL de autorización a partir de KEYCLOAK_PUBLIC_URL — el host por el que realmente se está navegando.

2

Keycloak autentica al usuario navegador

El formulario de login o registro se sirve en /realms/exchange-learning/protocol/openid-connect/auth, retransmitido por nginx directamente hacia el contenedor keycloak.

3

El navegador vuelve con un código navegador

Keycloak redirige a /oidc/callback/ con un code de autorización en el query string. Todavía no existe ningún token — el código es de un solo uso y de vida corta.

4

Django intercambia el código servidor a servidor

KeycloakOIDCAuthenticationBackend envía por POST el código a KEYCLOAK_INTERNAL_URL (http://keycloak:8080) directamente, con la cabecera Host fijada al nombre de host del paso 1. Keycloak devuelve un access token y un ID token.

5

Django obtiene el perfil servidor a servidor

El access token se envía al endpoint interno /userinfo, de nuevo con la cabecera Host correspondiente, para obtener los claims de correo y nombre.

6

Se crea o se empareja la cuenta local servidor

filter_users_by_claims busca un usuario de Django existente por nombre de usuario o correo; si no existe ninguno, create_user crea uno y la sesión inicia, aterrizando en /dashboard/.

Consola de administración de Keycloak

La consola administra ambos realms — master (el realm de administración propio de Keycloak) y exchange-learning (el realm de la aplicación, donde realmente viven sus usuarios y clientes).

URL de la consola
localhost/admin/master/console/
Servida a través de nginx → keycloak:8080. También accesible en 127.0.0.1 o en la IP de LAN.
Login de administrador
admin
La contraseña es la que se haya definido en KEYCLOAK_ADMIN_PASSWORD dentro de .env — no se repite aquí. Rótala antes de que esto salga de tu máquina.
Realm de la app
exchange-learning
Se cambia desde el desplegable de realm, arriba a la izquierda, una vez dentro de la consola.
Usuario de demo sembrado
demo.customer
Rol customer. La contraseña se define en keycloak/realm-export.json, dentro de la entrada credentials de este usuario, y se reimporta en cada volumen nuevo — no se repite aquí.

Qué estaba realmente roto

Dos errores distintos, ambos variaciones del mismo tema: una llamada que debía parecer que venía de localhost no lo parecía.

1 · 502 en /register/

carrera de arranque

nginx empezó a aceptar tráfico antes de que Keycloak terminara su primer arranque (inusualmente lento, ~76 minutos), así que la primerísima petición a /realms/…/auth chocó contra un puerto cerrado.

estado Transitorio — se resolvió solo una vez que Keycloak terminó de arrancar. Sin cambio de código; vale la pena añadir más adelante un healthcheck para que nginx lo espere.

2 · ConnectionError en /oidc/callback/

configuración
HTTPConnectionPool(host='localhost', port=80): Failed to establish a new connection

Los endpoints de token/userinfo/JWKS se construían a partir de KEYCLOAK_PUBLIC_URL (http://localhost). Llamado desde dentro del contenedor web, localhost significa el propio contenedor — ahí no escucha nada en el puerto 80.

arreglo Apuntar esos tres endpoints a KEYCLOAK_INTERNAL_URL (http://keycloak:8080) en settings.py, y evitar que LocalhostAutoDetectMiddleware los vuelva a sobrescribir con el host público en cada petición.

3 · 401 en /userinfo

configuración
401 Client Error: Unauthorized reason="Invalid token issuer. Expected 'http://keycloak:8080/realms/exchange-learning'"

Al arreglar el error 2 llamando directamente a keycloak:8080 apareció un desajuste nuevo: Keycloak estampa el claim iss de un token a partir de la cabecera Host usada para llegar a /auth — localhost — pero luego esperaba ese mismo Host también en las llamadas posteriores de token/userinfo. Llamarlo como keycloak:8080 hacía que Keycloak esperara un emisor (issuer) de keycloak:8080, que el token no tenía.

arreglo KeycloakOIDCAuthenticationBackend ahora sobrescribe get_token y get_userinfo para seguir llamando directamente a keycloak:8080, pero forzando la cabecera Host saliente a request.get_host() — el nombre de host que el navegador realmente usó.
