CURRENCY EXCHANGE SPRINT 1
GUÍA DE SECRETOS, CONFIGURACIÓN Y ARRANQUE

Este documento explica:
- cómo se plantillan (templan) los secretos a lo largo del proyecto
- qué valores deben configurarse y por qué
- qué hacer antes de arrancar el stack
- qué hacer después de que el stack esté corriendo
- los pasos prácticos recomendados para desarrolladores junior

------------------------------------------------------------
1) RESUMEN DE LOS ARCHIVOS DEL PROYECTO
------------------------------------------------------------

El proyecto se divide en unas pocas partes claras:

- docker-compose.yml
  Arranca PostgreSQL, Keycloak, Django y Nginx juntos.

- backend/Dockerfile
  Construye la imagen del contenedor de Django.

- backend/requirements.txt
  Lista las dependencias de Python.

- backend/config/settings.py
  Lee variables de entorno y configura Django, PostgreSQL y Keycloak OIDC.

- backend/config/urls.py
  Conecta las rutas del navegador con las vistas de Django y las rutas de OIDC.

- backend/core/views.py
  Maneja las páginas y los flujos de inicio de sesión/cierre de sesión/registro/eliminación.

- nginx/default.conf
  Reglas de proxy inverso para el tráfico del navegador.

- keycloak/realm-export.json
  Configuración inicial (bootstrap) del realm/cliente/roles/usuarios de Keycloak.

- postgres/init/01-create-databases.sql
  SQL de ejemplo para crear bases de datos y usuarios.

- .env.example
  Archivo plantilla que muestra las claves de configuración que el equipo debe proveer.

- .env
  Archivo de configuración local real usado por Docker Compose.

------------------------------------------------------------
2) CÓMO SE PLANTILLAN LOS SECRETOS
------------------------------------------------------------

La idea clave es:
- .env.example contiene marcadores de posición y valores de ejemplo seguros
- .env contiene los valores reales usados por el entorno local
- Django, Docker Compose y Keycloak leen desde variables de entorno
- los secretos nunca se codifican directamente (hardcode) en el código de la aplicación

Esto mantiene el código base reutilizable y reduce el riesgo de subir datos sensibles al repositorio.

Patrón de ejemplo:

- .env.example muestra:
  DJANGO_SECRET_KEY=change-me
- .env contiene:
  DJANGO_SECRET_KEY=tu-valor-secreto-real

El código de la aplicación entonces lee:

  os.getenv("DJANGO_SECRET_KEY")

Eso significa que al código no le importa cuál es el valor real. El valor se inyecta en tiempo de ejecución.

------------------------------------------------------------
3) QUÉ ARCHIVOS DEBEN USAR VARIABLES DE ENTORNO
------------------------------------------------------------

A) .env.example

Propósito:
- actúa como una lista de verificación de toda la configuración requerida
- seguro de subir al control de versiones
- ayuda a los nuevos desarrolladores a saber qué configurar

Qué debe contener:
- nombres de variables
- valores de ejemplo
- comentarios explicando cada variable

B) .env

Propósito:
- configuración local en tiempo de ejecución
- no se sube al control de versiones en un proyecto real

Qué debe contener:
- contraseñas reales
- claves secretas reales
- nombres de host y puertos correctos para el entorno actual

C) docker-compose.yml

Propósito:
- pasa valores de entorno a los contenedores
- define las dependencias entre servicios

Debe referenciar valores como:
- ${POSTGRES_USER}
- ${POSTGRES_PASSWORD}
- ${KEYCLOAK_ADMIN}
- ${DJANGO_SECRET_KEY}

Por qué:
- Compose puede sustituir los valores desde .env automáticamente
- los secretos no aparecen directamente en el archivo de Compose

D) backend/config/settings.py

Propósito:
- lee valores de entorno en tiempo de ejecución
- configura Django en base a esos valores

Debe leer valores de:
- clave secreta
- modo debug
- hosts permitidos
- nombre/usuario/contraseña/host/puerto de la base de datos
- endpoints y credenciales de cliente de Keycloak OIDC

Por qué:
- el mismo código puede correr en desarrollo local, pruebas y, más adelante, entornos parecidos a producción

E) keycloak/realm-export.json

Propósito:
- inicializa (bootstrap) la configuración del realm de Keycloak
- crea el cliente inicial, los roles y un usuario de ejemplo

Este archivo puede contener algunos marcadores de posición no sensibles para fines de aprendizaje, pero evita poner secretos reales aquí.

Por qué:
- la estructura del realm debe ser reproducible
- el equipo puede importar el mismo realm cada vez

F) nginx/default.conf

Propósito:
- reglas de proxy inverso
- aquí no debe guardarse ningún dato secreto

Por qué:
- Nginx solo necesita información de enrutamiento, no contraseñas

G) backend/Dockerfile

Propósito:
- construye la imagen de Django
- aquí no deben codificarse secretos

Por qué:
- la imagen del contenedor debe ser reutilizable y no estar atada a un único conjunto de secretos

------------------------------------------------------------
4) QUÉ SECRETOS O VALORES SENSIBLES DEBEN CONFIGURARSE
------------------------------------------------------------

Estos valores deben cambiarse respecto a los valores por defecto antes de un uso real.

1. DJANGO_SECRET_KEY
Por qué importa:
- Django lo usa para firmar sesiones, cookies y otros datos criptográficos
- debe ser aleatorio y privado

2. POSTGRES_PASSWORD
Por qué importa:
- protege al usuario de la base de datos de Django
- evita el acceso no autorizado a la base de datos

3. KEYCLOAK_DB_PASSWORD
Por qué importa:
- protege al usuario de la base de datos de Keycloak
- Keycloak almacena los datos de identidad en esta base de datos

4. KEYCLOAK_ADMIN_PASSWORD
Por qué importa:
- protege a la cuenta de administrador de Keycloak
- si se filtra, alguien podría gestionar todo el realm de identidad

5. KEYCLOAK_CLIENT_SECRET
Por qué importa:
- lo usa Django como secreto del cliente OIDC confidencial
- protege la relación de confianza entre Django y Keycloak

6. Valores de entorno opcionales pero importantes
- DJANGO_ALLOWED_HOSTS
- SITE_URL
- LOGIN_REDIRECT_URL
- LOGOUT_REDIRECT_URL
- KEYCLOAK_REALM
- KEYCLOAK_CLIENT_ID

Estos no son secretos, pero deben coincidir con tu configuración real.

------------------------------------------------------------
5) VALORES RECOMENDADOS A CONFIGURAR ANTES DE ARRANCAR
------------------------------------------------------------

Antes de ejecutar el stack por primera vez, actualiza:

- DJANGO_SECRET_KEY
- POSTGRES_PASSWORD
- KEYCLOAK_DB_PASSWORD
- KEYCLOAK_ADMIN_PASSWORD
- KEYCLOAK_CLIENT_SECRET

Enfoque recomendado para aprendizaje:
- mantén los nombres consistentes con el archivo de ejemplo
- reemplaza solo los valores
- usa un archivo .env por máquina de desarrollador

Convención de nombres sugerida:
- nombres de bases de datos: exchange_db y keycloak_db
- ID de cliente: exchange-web
- realm: exchange-learning

------------------------------------------------------------
6) QUÉ HACER ANTES DE ARRANCAR EL STACK
------------------------------------------------------------

Paso 1: instalar prerrequisitos
- Docker Engine
- plugin de Docker Compose
- Git
- un editor de código como VSCode

Paso 2: copiar el archivo de entorno de ejemplo
- copia .env.example a .env
- edita .env con valores locales reales

Paso 3: confirmar que los puertos están libres
- puerto 80 para Nginx
- puerto 8080 para Keycloak
- puerto 5432 para PostgreSQL si se expone localmente

Paso 4: revisar la estructura del proyecto
- backend/
- nginx/
- keycloak/
- postgres/

Paso 5: verificar que los marcadores de posición siguen siendo marcadores de posición
- ningún secreto debe subirse al control de versiones
- no deben usarse credenciales de producción en una máquina de aprendizaje

Paso 6: revisar el contexto de Docker
- el archivo backend/.dockerignore debe excluir .env y las cachés
- el .gitignore raíz debe excluir .env y los archivos generados

------------------------------------------------------------
7) CÓMO ARRANCAR EL STACK
------------------------------------------------------------

Ejecuta:

  docker compose up -d --build

Luego verifica:

  docker compose ps
  docker compose logs -f web
  docker compose logs -f keycloak
  docker compose logs -f nginx

Qué debería pasar:
- PostgreSQL arranca primero
- Keycloak espera a su base de datos
- Django espera a su base de datos
- Nginx espera a los servicios web y Keycloak

Si el stack falla, revisa los logs en este orden:
1. db o keycloak-db
2. keycloak
3. web
4. nginx

------------------------------------------------------------
8) CÓMO CONFIGURAR TODO UNA VEZ QUE ESTÁ CORRIENDO
------------------------------------------------------------

A) PostgreSQL

Qué revisar:
- el contenedor de la base de datos está saludable (healthy)
- Django puede conectarse
- las migraciones se ejecutan correctamente

Si algo falla:
- confirma POSTGRES_DB, POSTGRES_USER y POSTGRES_PASSWORD en .env
- confirma que el servicio Django usa POSTGRES_HOST=db

B) Keycloak

Abre la consola de administración en el navegador:
- http://localhost:8080

Inicia sesión con:
- KEYCLOAK_ADMIN
- KEYCLOAK_ADMIN_PASSWORD

Luego configura:
- nombre del realm: exchange-learning
- cliente: exchange-web
- URIs de redirección válidas
- orígenes web si es necesario
- registro de usuarios si se desea para el Sprint 1
- roles como customer y admin

El JSON del realm importado debería darte una base inicial, pero igual conviene verificarlo en la interfaz.

C) Django

Después de que el contenedor esté arriba, asegúrate de que:
- Django ve la base de datos
- Django puede cargar sus plantillas
- la ruta de login redirige a Keycloak
- la ruta de logout vuelve a la página de inicio

Si hace falta, ejecuta las migraciones manualmente:

  docker compose run --rm web python manage.py migrate

D) Nginx

Abre la aplicación a través de Nginx en el puerto 80.

Verifica que:
- la página de inicio carga
- las peticiones se redirigen (proxy) a Django
- las peticiones a rutas relacionadas con autenticación pueden llegar a Keycloak cuando corresponda

E) Páginas del frontend

Confirma que las páginas existen y cargan:
- /
- /login/
- /register/
- /dashboard/
- /account/
- /delete-account/

------------------------------------------------------------
9) LISTA DE VERIFICACIÓN RECOMENDADA DESPUÉS DEL ARRANQUE
------------------------------------------------------------

Una vez que el stack está corriendo, realiza estos pasos:

1. Abre la página de inicio a través de Nginx
2. Confirma que la marca muestra el nombre del negocio de cambio de divisas
3. Abre la consola de administración de Keycloak y verifica que el realm se importó correctamente
4. Crea o verifica el cliente de prueba
5. Confirma que las URIs de redirección son correctas
6. Confirma que el registro está habilitado si se requiere
7. Prueba el inicio de sesión desde el navegador
8. Prueba el cierre de sesión
9. Prueba el acceso a la página de cuenta estando autenticado
10. Prueba la página (placeholder) de eliminación de cuenta
11. Revisa los logs en busca de errores
12. Confirma que los contenedores de base de datos conservan sus datos en volúmenes

------------------------------------------------------------
10) CÓMO DESARROLLAR DESPUÉS DEL PRIMER ARRANQUE
------------------------------------------------------------

Ciclo de desarrollo recomendado:

1. cambia un archivo
2. reconstruye o reinicia el contenedor correspondiente
3. revisa los logs
4. prueba un flujo de usuario
5. confirma (commit) el cambio en una rama de funcionalidad
6. abre un PR hacia development

Comandos útiles:

  docker compose up -d --build
  docker compose restart web
  docker compose restart keycloak
  docker compose restart nginx
  docker compose logs -f web
  docker compose down
  docker compose down -v

------------------------------------------------------------
11) COPIA CONDENSADA DE LA EXPLICACIÓN ANTERIOR
------------------------------------------------------------

El proyecto está diseñado como un stack de aprendizaje pequeño pero realista:
- Django maneja las páginas web y la lógica de la aplicación
- Keycloak maneja la identidad de usuario y el login/registro
- PostgreSQL almacena los datos de aplicación e identidad
- Nginx enruta el tráfico del navegador hacia el servicio correcto
- Docker Compose ejecuta todo junto en Debian

Este es el arreglo correcto para el Sprint 1 porque es simple, modular y fácil de depurar.

------------------------------------------------------------
12) REGLAS PRÁCTICAS PARA EL EQUIPO
------------------------------------------------------------

- no codificar secretos (hardcode) en archivos Python
- no subir .env al repositorio
- usar .env.example como plantilla de configuración
- mantener los nombres de realm/cliente consistentes entre archivos
- mantener legible el archivo de Docker Compose
- mantener Nginx simple hasta que el primer login extremo a extremo funcione
- usar ramas y PRs pequeños
- revisar los logs antes de cambiar varios archivos a la vez

------------------------------------------------------------
13) CONSEJO FINAL
------------------------------------------------------------

Si eres nuevo en este stack, haz el trabajo en este orden:

1. configura los secretos
2. arranca PostgreSQL
3. arranca Keycloak
4. arranca Django
5. añade el enrutamiento de Nginx
6. prueba el login y el logout
7. luego mejora la interfaz

Esa secuencia reduce la confusión y hace la depuración mucho más fácil.
