Reference — exchange‑learning realm

Exchange Pro Access Guide

How sign‑in and registration work end to end, where the Keycloak admin console lives, and the issuer‑mismatch bug that was blocking every login until today.

Stack Django 5.1 + mozilla‑django‑oidc + Keycloak 25.0.6 Realm exchange-learning Updated 4 Sep 2026

Two doors into the same realm

Every request either comes from a browser through nginx, or from the Django container talking to Keycloak directly. The two doors must claim the same hostname, or Keycloak refuses the token.

The rule: whichever hostname the browser used to reach nginx — localhost, 127.0.0.1 or a LAN IP — every later server‑to‑server call for that same session must present that exact string as its Host header, even though it physically dials keycloak:8080 on the Docker network.

Sign‑in & registration flow

Both /login/ and /register/ land on the same OpenID Connect exchange; registration just adds kc_action=register so Keycloak opens on its sign‑up tab instead of sign‑in.

1

Django redirects to Keycloak browser

views.login_view / register_view send the browser to oidc_authentication_init, which builds the authorize URL from KEYCLOAK_PUBLIC_URL — the host you're actually browsing on.

2

Keycloak authenticates the user browser

Login or registration form is served at /realms/exchange-learning/protocol/openid-connect/auth, proxied by nginx straight through to the keycloak container.

3

Browser returns with a code browser

Keycloak redirects to /oidc/callback/ with an authorization code in the query string. No tokens exist yet — the code is single‑use and short‑lived.

4

Django exchanges the code server‑to‑server

KeycloakOIDCAuthenticationBackend POSTs the code to KEYCLOAK_INTERNAL_URL (http://keycloak:8080) directly, with the Host header pinned to the hostname from step 1. Keycloak returns an access token and ID token.

5

Django fetches the profile server‑to‑server

The access token is sent to the internal /userinfo endpoint, again with the matching Host header, to pull email and name claims.

6

Local account is created or matched server

filter_users_by_claims looks up an existing Django user by username or email; if none exists, create_user makes one and the session logs in, landing on /dashboard/.

Keycloak admin console

The console manages both realms — master (Keycloak's own admin realm) and exchange-learning (the app's realm, where its users and clients actually live).

Console URL
localhost/admin/master/console/
Proxied by nginx → keycloak:8080. Also reachable on 127.0.0.1 or the LAN IP.
Admin login
admin
Password is whatever KEYCLOAK_ADMIN_PASSWORD is set to in .env — not repeated here. Rotate it before this leaves your machine.
App realm
exchange-learning
Switch to it from the realm dropdown, top left, once inside the console.
Seeded demo user
demo.customer
Role customer. Password is set in keycloak/realm-export.json under this user's credentials entry, re‑imported on every fresh volume — not repeated here.

Clients & roles in the realm

Three registered clients, each with a narrow job. Only exchange-web is reachable from a browser.

ClientUsed byGrantCan reach browser?
exchange-web The Django app itself — login, register, logout Authorization code Yes
exchange-admin-api KeycloakAdminClient — deletes a user's Keycloak account when they delete their Django account Client credentials No
security-admin-console Keycloak's own admin UI (built in) Authorization code Yes

Realm roles are defined but not yet enforced anywhere in Django: customer (assigned to demo.customer) and admin. Wiring these into verify_claims or a permission check is open work.

What was actually broken

Two separate bugs, both variations on the same theme: a call that should have looked like it came from localhost didn't.

1 · 502 on /register/

startup race

nginx started accepting traffic before Keycloak had finished its (unusually slow, ~76‑minute) first boot, so the very first request to /realms/…/auth hit a closed port.

status Transient — resolved itself once Keycloak finished starting. No code change; worth adding a healthcheck later so nginx waits on it.

2 · ConnectionError at /oidc/callback/

config
HTTPConnectionPool(host='localhost', port=80): Failed to establish a new connection

The token/userinfo/JWKS endpoints were built from KEYCLOAK_PUBLIC_URL (http://localhost). Called from inside the web container, localhost means the container itself — nothing listens on port 80 there.

fix Point those three endpoints at KEYCLOAK_INTERNAL_URL (http://keycloak:8080) in settings.py, and stop LocalhostAutoDetectMiddleware from overwriting them back to the public host on every request.

3 · 401 on /userinfo

config
401 Client Error: Unauthorized reason="Invalid token issuer. Expected 'http://keycloak:8080/realms/exchange-learning'"

Fixing #2 by calling keycloak:8080 directly introduced a new mismatch: Keycloak stamps a token's iss claim from the Host header used to reach /auth — localhost — but then expected that same Host on the later token/userinfo calls too. Calling it as keycloak:8080 made Keycloak expect an issuer of keycloak:8080, which the token didn't have.

fix KeycloakOIDCAuthenticationBackend now overrides get_token and get_userinfo to keep dialing keycloak:8080 directly, but forces the outgoing Host header to request.get_host() — the hostname the browser actually used.
