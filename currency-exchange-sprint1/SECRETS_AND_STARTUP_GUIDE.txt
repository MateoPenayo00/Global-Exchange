CURRENCY EXCHANGE SPRINT 1
SECRETS, CONFIGURATION, AND STARTUP GUIDE

This document explains:
- how secrets are templated across the project
- which values must be configured and why
- what to do before starting the stack
- what to do after the stack is running
- the practical steps recommended for junior developers

------------------------------------------------------------
1) SUMMARY OF THE PROJECT FILES
------------------------------------------------------------

The project is split into a few clear parts:

- docker-compose.yml
  Starts PostgreSQL, Keycloak, Django, and Nginx together.

- backend/Dockerfile
  Builds the Django container image.

- backend/requirements.txt
  Lists Python dependencies.

- backend/config/settings.py
  Reads environment variables and configures Django, PostgreSQL, and Keycloak OIDC.

- backend/config/urls.py
  Connects browser routes to Django views and OIDC routes.

- backend/core/views.py
  Handles the pages and the login/logout/register/delete flows.

- nginx/default.conf
  Reverse proxy rules for browser traffic.

- keycloak/realm-export.json
  Keycloak realm/client/role/user bootstrap configuration.

- postgres/init/01-create-databases.sql
  Example SQL for creating databases and users.

- .env.example
  Template file showing the configuration keys the team must provide.

- .env
  Real local configuration file used by Docker Compose.

------------------------------------------------------------
2) HOW THE SECRETS ARE TEMPLATED
------------------------------------------------------------

The key idea is:
- .env.example contains placeholders and safe example values
- .env contains the actual values used by the local environment
- Django, Docker Compose, and Keycloak read from environment variables
- secrets are never hardcoded into application code

This keeps the codebase reusable and reduces the risk of committing sensitive data.

Example pattern:

- .env.example shows:
  DJANGO_SECRET_KEY=change-me
- .env contains:
  DJANGO_SECRET_KEY=your-real-secret-value

The application code then reads:

  os.getenv("DJANGO_SECRET_KEY")

That means the code does not care what the real value is. The value is injected at runtime.

------------------------------------------------------------
3) WHICH FILES SHOULD USE ENVIRONMENT VARIABLES
------------------------------------------------------------

A) .env.example

Purpose:
- acts as a checklist of all required settings
- safe to commit to version control
- helps new developers know what to configure

What it should contain:
- variable names
- sample values
- comments explaining each variable

B) .env

Purpose:
- local runtime configuration
- not committed to version control in a real project

What it should contain:
- real passwords
- real secret keys
- correct hostnames and ports for the current environment

C) docker-compose.yml

Purpose:
- passes environment values into containers
- defines service dependencies

It should reference values like:
- ${POSTGRES_USER}
- ${POSTGRES_PASSWORD}
- ${KEYCLOAK_ADMIN}
- ${DJANGO_SECRET_KEY}

Why:
- Compose can substitute the values from .env automatically
- secrets do not appear directly in the Compose file

D) backend/config/settings.py

Purpose:
- reads environment values at runtime
- configures Django based on those values

It should read values for:
- secret key
- debug mode
- allowed hosts
- database name/user/password/host/port
- Keycloak OIDC endpoints and client credentials

Why:
- the same code can run in local development, testing, and later production-like environments

E) keycloak/realm-export.json

Purpose:
- bootstraps Keycloak realm configuration
- creates the initial client, roles, and sample user

This file may contain some non-sensitive placeholders for learning, but avoid putting real secrets in it.

Why:
- realm structure should be reproducible
- the team can import the same realm every time

F) nginx/default.conf

Purpose:
- reverse proxy rules
- no secret data should be stored here

Why:
- Nginx only needs routing information, not passwords

G) backend/Dockerfile

Purpose:
- builds the Django image
- no secrets should be hardcoded here

Why:
- the container image should be reusable and not tied to one secret set

------------------------------------------------------------
4) WHICH SECRETS OR SENSITIVE VALUES MUST BE CONFIGURED
------------------------------------------------------------

These values should be changed from the defaults before real use.

1. DJANGO_SECRET_KEY
Why it matters:
- Django uses it to sign sessions, cookies, and other cryptographic data
- it must be random and private

2. POSTGRES_PASSWORD
Why it matters:
- protects the Django database user
- prevents unauthorized database access

3. KEYCLOAK_DB_PASSWORD
Why it matters:
- protects the Keycloak database user
- Keycloak stores identity data in this database

4. KEYCLOAK_ADMIN_PASSWORD
Why it matters:
- protects the Keycloak administrator account
- if leaked, someone could manage the whole identity realm

5. KEYCLOAK_CLIENT_SECRET
Why it matters:
- used by Django as the confidential OIDC client secret
- protects the trust relationship between Django and Keycloak

6. Optional but important environment values
- DJANGO_ALLOWED_HOSTS
- SITE_URL
- LOGIN_REDIRECT_URL
- LOGOUT_REDIRECT_URL
- KEYCLOAK_REALM
- KEYCLOAK_CLIENT_ID

These are not secrets, but they must match your real setup.

------------------------------------------------------------
5) RECOMMENDED VALUES TO CONFIGURE BEFORE STARTING
------------------------------------------------------------

Before you run the stack for the first time, update:

- DJANGO_SECRET_KEY
- POSTGRES_PASSWORD
- KEYCLOAK_DB_PASSWORD
- KEYCLOAK_ADMIN_PASSWORD
- KEYCLOAK_CLIENT_SECRET

Recommended approach for learning:
- keep the names consistent with the sample file
- replace only the values
- use one .env file per developer machine

Suggested naming convention:
- database names: exchange_db and keycloak_db
- client ID: exchange-web
- realm: exchange-learning

------------------------------------------------------------
6) WHAT TO DO BEFORE STARTING THE STACK
------------------------------------------------------------

Step 1: install prerequisites
- Docker Engine
- Docker Compose plugin
- Git
- a code editor such as VSCode

Step 2: copy the example environment file
- copy .env.example to .env
- edit .env with real local values

Step 3: confirm ports are free
- port 80 for Nginx
- port 8080 for Keycloak
- port 5432 for PostgreSQL if exposed locally

Step 4: review the project structure
- backend/
- nginx/
- keycloak/
- postgres/

Step 5: verify the placeholders are still placeholders
- no secrets should be committed to source control
- no production credentials should be used on a learning machine

Step 6: check the Docker context
- the backend/.dockerignore file should exclude .env and caches
- the root .gitignore should exclude .env and generated files

------------------------------------------------------------
7) HOW TO START THE STACK
------------------------------------------------------------

Run:

  docker compose up -d --build

Then verify:

  docker compose ps
  docker compose logs -f web
  docker compose logs -f keycloak
  docker compose logs -f nginx

What should happen:
- PostgreSQL starts first
- Keycloak waits for its database
- Django waits for its database
- Nginx waits for the web and Keycloak services

If the stack fails, check the logs in that order:
1. db or keycloak-db
2. keycloak
3. web
4. nginx

------------------------------------------------------------
8) HOW TO CONFIGURE EVERYTHING ONCE IT IS RUNNING
------------------------------------------------------------

A) PostgreSQL

What to check:
- the database container is healthy
- Django can connect
- migrations run successfully

If something fails:
- confirm POSTGRES_DB, POSTGRES_USER, and POSTGRES_PASSWORD in .env
- confirm the Django service uses POSTGRES_HOST=db

B) Keycloak

Open the admin console in the browser:
- http://localhost:8080

Log in with:
- KEYCLOAK_ADMIN
- KEYCLOAK_ADMIN_PASSWORD

Then configure:
- realm name: exchange-learning
- client: exchange-web
- valid redirect URIs
- web origins if needed
- user registration if desired for Sprint 1
- roles such as customer and admin

The imported realm JSON should give you a baseline, but you should still verify it in the UI.

C) Django

After the container is up, ensure:
- Django sees the database
- Django can load its templates
- the login route redirects to Keycloak
- the logout route returns to the landing page

If needed, run migrations manually:

  docker compose run --rm web python manage.py migrate

D) Nginx

Open the app through Nginx on port 80.

Check that:
- the landing page loads
- requests are proxied to Django
- requests for auth-related paths can reach Keycloak when configured

E) Frontend pages

Confirm that the pages exist and load:
- /
- /login/
- /register/
- /dashboard/
- /account/
- /delete-account/

------------------------------------------------------------
9) RECOMMENDED POST-START CHECKLIST
------------------------------------------------------------

After the stack is running, perform these steps:

1. Open the landing page through Nginx
2. Confirm the branding shows the currency exchange business name
3. Open Keycloak admin console and verify the realm imported correctly
4. Create or verify the test client
5. Confirm the redirect URIs are correct
6. Confirm registration is enabled if required
7. Test login from the browser
8. Test logout
9. Test account page access when authenticated
10. Test the delete-account placeholder page
11. Review logs for errors
12. Confirm the database containers keep their data in volumes

------------------------------------------------------------
10) HOW TO DEVELOP AFTER THE FIRST START
------------------------------------------------------------

Recommended development cycle:

1. change one file
2. rebuild or restart the relevant container
3. check logs
4. test one user flow
5. commit the change in a feature branch
6. open a PR into development

Useful commands:

  docker compose up -d --build
  docker compose restart web
  docker compose restart keycloak
  docker compose restart nginx
  docker compose logs -f web
  docker compose down
  docker compose down -v

------------------------------------------------------------
11) COPY OF THE EARLIER EXPLANATION, CONDENSED
------------------------------------------------------------

The project is designed as a small but realistic learning stack:
- Django handles the web pages and app logic
- Keycloak handles user identity and login/registration
- PostgreSQL stores application and identity data
- Nginx routes browser traffic to the right service
- Docker Compose runs everything together on Debian

This is the right arrangement for Sprint 1 because it is simple, modular, and easy to troubleshoot.

------------------------------------------------------------
12) PRACTICAL RULES FOR THE TEAM
------------------------------------------------------------

- do not hardcode secrets in Python files
- do not commit .env
- use .env.example as the template for configuration
- keep the realm/client names consistent across files
- keep the Docker Compose file readable
- keep Nginx simple until the first end-to-end login works
- use small branches and small PRs
- review logs before changing multiple files at once

------------------------------------------------------------
13) FINAL ADVICE
------------------------------------------------------------

If you are new to this stack, do the work in this order:

1. configure secrets
2. start PostgreSQL
3. start Keycloak
4. start Django
5. add Nginx routing
6. test login and logout
7. then improve the UI

That sequence reduces confusion and makes debugging much easier.
